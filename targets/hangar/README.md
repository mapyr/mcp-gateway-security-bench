# targets/hangar — MCP Hangar adapter (WS-8)

[MCP Hangar](https://github.com/mapyr/mcp-hangar) is an MCP intermediary. **It is
maintained by this bench's author.**

## Conflict-of-interest guardrails (GOVERNANCE §1)

* Hangar is implemented **last** of the targets, on purpose — the harness grew
  around three other targets first, so it cannot have been shaped to fit Hangar.
* Hangar runs through the **same pipeline and adapter contract** as every other
  target. No hand-tuning "to make it pass."
* **No MCPSB result appears in Hangar's own marketing until at least one external
  maintainer has published their own run** (§1.4). Until then a "passes MCPSB"
  claim would be self-reference.
* The capability map below was derived from Hangar's source with the **same
  skeptical, enforcement-must-be-in-code standard** applied to ToolHive and
  Docker MCP Gateway — a capability is declared only where the code enforces it.
* **Version provenance.** The map reflects Hangar's **v2 authorization model**
  (per-caller authz, tool allow/deny, tenancy — features the v2 line introduced).
  The adapter pins a tested floor of **v2.17.1** (`supports_version`), so running
  it against a pre-v2 build (e.g. 1.4.0, which predates per-tool authorization)
  yields `ERROR` — verdict withheld — not stale `FAIL`s. Re-review the map when
  raising the floor.

## Capability map

Applied honestly, that standard **declares capabilities Hangar offers even where
enforcement is incomplete**, so the corresponding tests *run* and reveal the gap
as `FAIL` when run live — rather than hiding the gap behind `UNSUPPORTED`. Hiding
them is the exact COI failure this project exists to prevent.

| Concept | Hangar | Note |
| --- | --- | --- |
| MCP proxy: tools/list, tools/call | ✅ | Streamable HTTP at `/mcp` |
| prompts/get, resources/read | ❔ not declared | no evidence of proxying in the surface reviewed → `UNSUPPORTED` |
| Batch / aggregating path | ✅ | per-call gated fan-out |
| Authentication (JWT/OIDC + API key) | ✅ (opt-in) | non-loopback bind refused without auth |
| Principal binding / token expiry / audience (RFC 8707) | ✅ | verified in the auth path |
| Per-caller authorization | ✅ | dual fail-closed deny engines, call-time |
| Tool allow/deny policy | ✅ | per-tenant, enforced |
| Tenancy (tenant from verified token; headers/`_meta` not trusted) | ✅ | strong; anti-spoof tested |
| Name-collision / shadowing control | ✅ | colliding names dropped fail-safe |
| Schema/digest pinning | ⚠️ partial | digest re-verified on `tools/call` against an operator pin; full coverage not verified by this bench |
| Egress / SSRF control | ⚠️ declared, not fully verified | an egress control is offered; end-to-end enforcement is not vouched for by this bench (see disclosure note) |
| Audit logging | ⚠️ partial | call-path events emitted; redaction/durability not vouched for by this bench (see disclosure note) |
| Session isolation across reconnect | ❔ not declared | no evidence → `UNSUPPORTED` |
| Gateway-layer secret isolation | ❔ not declared | not a boundary the gateway-layer test can probe → `UNSUPPORTED` |

## Expected verdict profile

Validated in `tests/test_hangar_adapter.py` (capability-driven; the live PASS/FAIL
are produced only by an actual run).

* **`UNSUPPORTED` (6):** AUTHZ-001.c/.d, AUTHZ-003.c/.d (prompts/resources
  surfaces), SESSION-001.f, SECRET-001.b.
* **Runs live:** everything else — including the egress, audit, and schema

  publish (GOVERNANCE §1.3) — rather than published as a roadmap.

## Running it live

Honest provisioning (invariant #8): without the harness the adapter is
unavailable and every test is `INCONCLUSIVE`. A faithful run needs:

1. Hangar installed (`pip install mcp-hangar`) and started **with auth enabled**
   (`mcp-hangar serve --config config.yaml --http`) — not the `--unsafe-no-auth`
   demo posture.
2. An OIDC issuer minting the principals' tokens; export `MCPSB_HANGAR_OIDC_ISSUER`,
   `MCPSB_HANGAR_OIDC_AUDIENCE`, `MCPSB_HANGAR_TOKEN_A/B` (+ `_EXPIRED`, `_WRONGAUD`).
3. A config generated by `targets/hangar/config.py` (auth block + enforced tool
   policy), pointing Hangar at a comprehensive fixture MCP server.

The transport client (`mcpsb/streamable.py`, `/mcp`) is shared with the other
targets, so the attack corpus is unchanged.

## Status

Adapter, capability map, and config translation are complete and unit-tested.
**A live auth run has been done** (`mcp-hangar serve --http` with OIDC pointed at
the bench's issuer harness, proxying the stdio fixture):

* **AUTH-001, AUTH-003, AUTH-004 PASS** (5 sub-IDs) with a **verified positive
  control** (a valid token is accepted) — Hangar genuinely enforces JWT
  signature, expiry, and audience.
* **TENANT-001, TENANT-002 PASS** — tenant comes only from the verified token
  claim; a client cannot supply or override it via an argument, header, or
  `_meta` (shown via the `require_tenant` fail-closed gate).

This covers the auth and tenancy families. It does **not** vouch for the egress
or audit
families, where the source review found enforcement gaps and which were not
reachable live here — a live AUTH PASS is not a clean bill of health. Full record:
[`results/live/hangar.md`](../../results/live/hangar.md). Because Hangar is the
author's own target, its `results/` may be published without embargo
(SECURITY.md), but the §1.4 marketing rule still applies.
